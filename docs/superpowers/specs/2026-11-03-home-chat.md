# Spec: Home is M8 chat

Status: approved 2026-11-03 (open questions answered: Today numbers → Analytics → Month; + in the chat header; no status line). Owner request: "change the home page to be a simple chat interface, like ChatGPT / Claude. It should have the context of all my data, plus historical conversations about my finances."

## Objective
The first tab becomes a full-screen chat with M8. The Owner opens the app and types a question; M8 answers from their whole ledger and can advise. Past conversations are kept and can be reopened, renamed by their first question, and deleted.

User stories
- As the Owner, I open Ledger and land in a chat with a big input, not a dashboard.
- I ask "how much did I spend on food in August?" and get a grounded answer from my data.
- I ask "how am I doing this month?" and M8 knows my budget, accounts, goals and month so far without me explaining.
- I tap a history button, see my past conversations (newest first, titled by their first question, dated), reopen one and continue it.
- I start a new conversation with one tap. I can delete a conversation.
- History survives closing the app and is the same on any device I sign in on (cloud mode).

## Assumptions (correct these before Plan)
1. Tab bar becomes **Chat · Money · Analytics**. `/today` routes to the chat. The `/chat` route is folded into it.
2. What the current Today page shows (left to spend, budget, category budgets, goals) moves to **Analytics → Month** as a "Budget & goals" block, so nothing is lost. (See Open question 1.)
3. The yellow **+** stays on Money and Analytics. On the chat tab, logging stays available from a small + in the chat header, so it never covers the composer.
4. "Context of all my data": M8 already reads the ledger through read-only tools (any period, any category, top entries, budget status). We add an always-on **snapshot** to each request (this month's in/out, left to spend, budget, account balances, goals) so common questions need no tool round.
5. History is stored server-side in two new tables, `chat_threads` and `chat_messages` (RLS: owner only), written by the chat function. Local (no-cloud) mode keeps threads in localStorage.
6. The model gets the current thread's last 12 turns (as today). Other threads are not sent to the model.
7. Wording stays "M8"; no streaming change (answers still reveal word by word after arrival).

## Tech Stack

## Testing Strategy
- Client: thread store (create, append, list order, delete, local fallback); routing (`/today` → chat, `/chat` redirect).
- DB (pglite): RLS — a user sees only their threads/messages; delete cascades.
- Functions: snapshot built from the ledger; chat writes the user turn and the answer to the thread.
- Manual: demo mode in the browser; cloud mode after deploy.

## Boundaries
- Always: new numbered migration (never edit applied ones); keep `respond()` local fallback working; tests + types + build green before commit.
- Ask first: dropping or renaming any existing table; sending other threads to the model; deploying.
- Never: send another user's data; store secrets in the client; remove the Today data without a new home for it.

## Success Criteria
1. Opening the app lands on the chat (empty state: greeting + 3–4 suggestions + composer).
2. A question about any month/category/account is answered from data (cloud) or by the local rules (demo).
3. Each request carries the snapshot; "how am I doing this month?" is answered in one tool round or none.
4. History: new thread per conversation; list shows title (first question, ≤ 60 chars), date; reopen continues it; delete removes it; persists across reloads and devices (cloud).
5. Left to spend, budget, category budgets and goals are reachable in Analytics → Month.
6. All tests, types, lint, build pass.

## Plan
Contract first, then three parallel tracks.

**Contract (cloud)**
- `chat_threads(id uuid pk, user_id, title text, created_at, updated_at)`; `chat_messages(id uuid pk, thread_id → chat_threads on delete cascade, user_id, role 'user'|'assistant', text, answer jsonb null, created_at)`. RLS: owner select/insert/update/delete.
- `POST /functions/v1/chat` body `{ messages, tz, thread_id? }` → response gains `thread_id`. The function creates the thread (title = first question, ≤ 60 chars) when `thread_id` is missing or unknown, appends the user turn and the answer, bumps `updated_at`.
- Client reads/deletes threads directly through supabase-js (RLS scopes them).
- Every request's context carries a snapshot: month in/out so far, left to spend and daily allowance (`today_budget`), account balances, goals.

**Tracks**
1. Server: migration + RLS + pglite tests; chat function persistence + snapshot + function tests.
2. Analytics: "Budget & goals" block in Month (left to spend, budget bar, category budgets, goals, Show the math) reusing `plan.tsx` / `today-sheets.tsx`; Today screen retired.
3. Client chat: thread store (local + cloud), chat as the home tab with history sheet, New chat, + in header; routes and tab bar.
